# Practical 8 — Performance Optimization and Lazy Loading (Notes & Viva)

## 1. What Was Built
1. **Route-Based Code Splitting:**
   - Transformed static route imports in `src/App.jsx` into dynamic imports using React's `lazy` and `Suspense`.
   - Extracted routes into separate chunks: `Home`, `Projects`, `Contact`, `Login`, `Register`, and `NotFound`.
   - Wrapped exclusively the `<Routes>` block in `<Suspense fallback={<PageLoader />}>`, ensuring navigation elements (`NavBar`, `Footer`) remain mounted and visible during page transitions.
2. **Accessible, Flicker-Free Fallback:**
   - Implemented `components/PageLoader.jsx` with an accessible spinner (`role="status"`, `aria-live="polite"`).
   - Created the `lazyWithMinDelay(factory, ms=300)` helper in `src/utils/lazyWithDelay.js` that combines the dynamic import Promise with a 300ms minimum timeout to prevent UI flickering on fast connections while providing a smooth loader on slow connections.
3. **Heavy Third-Party Component Splitting (`recharts`):**
   - Installed `recharts` and created `components/TaskStatsChart.jsx` providing visual bar and pie chart analytics of completed vs. pending tasks and tasks by priority.
   - Integrated on-demand lazy loading for `TaskStatsChart` in `Projects.jsx` behind a "Show Visual Analytics" button with its own localized `<Suspense>` boundary.
   - Result: Recharts (a 397 kB bundle) is completely isolated into its own chunk, incurring **zero** initial download overhead.
4. **Re-render Optimization with `React.memo` & `useCallback`:**
   - Profiled task list re-renders when typing in the search box or task form.
   - Wrapped `TaskItem` and `TaskList` in `React.memo` and wrapped action handlers (`addTask`, `editTask`, `removeTask`, `handleToggleComplete`, `handleEdit`, `handleDelete`) in `useCallback`.
   - Result: Typing in the search input or task description no longer triggers re-rendering of existing `TaskItem` components whose props remain unchanged.

## 2. Key Questions (Assignment & PDF Requirements)

### Q1: What is the difference between the initial bundle and a lazy chunk, and when are they downloaded?
- **Initial Bundle:** The critical JavaScript payload (`index-[hash].js`) loaded immediately when the user first visits the web application. It contains the core React runtime, router configuration, layout components (`NavBar`, `Footer`), authentication context, and code necessary for the initial paint.
- **Lazy Chunk:** An isolated, split JavaScript file (`Projects-[hash].js`, `TaskStatsChart-[hash].js`) generated by dynamic `import()`. It is **not** downloaded during the initial page request. Instead, the browser requests the file via network only when the user navigates to the associated route or triggers the component render condition (e.g., clicking "Show Visual Analytics").

### Q2: Why does perceived performance improve even if total code size remains the same?
Perceived performance depends primarily on **Time to Interactive (TTI)** and **First Contentful Paint (FCP)**.
- While the total combined size of all chunks is identical (or slightly larger due to module glue and runtime headers), the browser only downloads, parses, compiles, and evaluates the critical shell on initial visit.
- Offloading 397 kB of charting libraries and secondary pages means the main thread is freed faster, leading to quicker initial page rendering and responsive interaction. The remaining assets load asynchronously in the background when requested.

### Q3: When is code splitting NOT worth it?
1. **Very Small Applications:** If the entire codebase is only 50–100 kB, splitting it into tiny 2–3 kB micro-chunks adds HTTP request overhead, connection round-trips, and bundle glue without meaningful performance gain.
2. **Critical Above-the-Fold Content:** Lazy loading components required immediately on the landing page creates unnecessary request waterfalls, layout shifts (CLS), and spinner flashes.
3. **High-Latency / Offline-Unstable Networks:** If a user loses connection after initial load and clicks a lazy-loaded route, navigation will fail unless robust offline caching (Service Workers) is present.

## 3. Reflection & Errors Encountered

1. **Error: Fast network loader flicker**
   - *Problem:* On fast networks, dynamic imports resolve in 20–50 ms, causing `PageLoader` to flash abruptly on screen for a split second before vanishing.
   - *Fix:* Created `lazyWithMinDelay(factory, ms=300)` helper that executes `Promise.all([factory(), new Promise(r => setTimeout(r, ms))])`, ensuring any visible fallback displays smoothly for at least 300 ms.
2. **Error: Monolithic third-party library inflating entry bundle**
   - *Problem:* Adding `recharts` for task statistics threatened to bloat the main JS bundle by ~400 kB.
   - *Fix:* Wrapped `TaskStatsChart` in `lazy()` and rendered it conditionally behind user intent (`showStats === true`) with its own scoped `<Suspense>` container. Build logs confirm `TaskStatsChart-BGzVBDX-.js` (397.18 kB) is completely segregated into a separate chunk.
3. **Error: Redundant list re-renders during search typing**
   - *Problem:* Typing into the search input re-rendered the parent `Projects` page on every keystroke, causing all `TaskItem` components in the list to re-render.
   - *Fix:* Wrapped `TaskItem` and `TaskList` in `React.memo` and memoized all action handlers in `useTasks.js` and `Projects.jsx` with `useCallback`. Props stability was preserved, preventing redundant child re-renders.

## 4. 5 Likely Viva Questions & Concise Answers

### 1. How does `React.lazy` work under the hood?
`React.lazy` takes a factory function that calls dynamic `import()`. It returns a React component that suspends rendering until the dynamic import Promise resolves with an ES module containing a `default` export. During suspension, React traverses up to the nearest `<Suspense>` boundary and renders its `fallback`.

### 2. Why must the `<Suspense>` boundary wrap only `<Routes>` rather than the entire `<App>`?
Wrapping only `<Routes>` preserves persistent layout components like `<NavBar>` and `<Footer>`. When navigating to a new route, the navigation bar stays interactive and visible while only the page content area shows the loader, preventing disorienting layout flash.

### 3. What is the role of `React.memo` and `useCallback` in list performance?
`React.memo` performs a shallow comparison of a component's props and skips re-rendering if props haven't changed. If parent callback functions passed to the child are recreated on every render, the shallow comparison fails; `useCallback` ensures function references remain identical between renders unless dependencies change.

### 4. What is a chunk in Vite/Rollup and how is it named?
A chunk is a separate JavaScript output file produced by the bundler when it encounters a dynamic import (`import(...)`) or a manual code-splitting configuration (`splitChunks` / `manualChunks`). Vite appends a content hash to the chunk filename (e.g., `Projects-DXR1PEmz.js`) for long-term HTTP browser caching.

### 5. How can you verify in browser DevTools that lazy loading is functioning properly?
Open Chrome DevTools -> **Network** tab -> filter by **JS** -> disable cache -> throttle network to "Slow 3G" or "Fast 3G". On initial load, verify only `index-[hash].js` is downloaded. When clicking on the "Projects" link, verify a new request for `Projects-[hash].js` appears in the network waterfall while the `<PageLoader />` fallback is displayed.
