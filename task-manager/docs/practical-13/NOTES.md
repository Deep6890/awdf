# Practical 13 — AI API Integration with Groq (Notes & Viva)

## 1. What Was Built
1. **Server-Side AI Proxy Service (`services/groq.js`):**
   - Direct integration with the **Groq API** (`https://api.groq.com/openai/v1/chat/completions`) using Node's built-in `fetch` and `AbortController` timeout (`AI_TIMEOUT_MS=8000`).
   - Uses `llama-3.1-8b-instant` model with temperature 0.5 and 120 max tokens.
   - Restrictive system prompt enforcing concise, unformatted 1–2 sentence descriptions.
   - Zero SDK dependencies; zero API key leakage to the frontend.
2. **AI Endpoint (`controllers/aiController.js` & `routes/aiRoutes.js`):**
   - Protected endpoint: `POST /api/ai/generate-description`.
   - Secured with JWT `auth` middleware and input validation (`validate({ title: { required: true, max: 100 } })`).
   - Enhanced with `middleware/aiRateLimit.js` restricting requests to 1 request per user per task title per 60 seconds (returns HTTP 429 when exceeded).
3. **Graceful Degradation Architecture:**
   - Any failure (invalid API key, upstream Groq 429/500, network timeout, or service downtime) catches internally and returns HTTP 200 with `{ description: "", fallback: true, message: "..." }`.
   - The user interface smoothly falls back to manual typing without disrupting task creation or navigation.
4. **Client UI Integration (`TaskForm.jsx`):**
   - "Generate with AI" button with `Sparkles` icon next to the description field.
   - Disabled when the title is empty or during active generation.
   - Real-time loading indicator (`Generating...` with spinner).
   - Generated suggestion fills the description textarea as editable text.
   - Prominent transparency disclaimer: *"AI-generated suggestion — please review before saving."*
5. **Comprehensive Test Suite (`tests/ai.test.js`):**
   - Verified 5 automated test cases: success path, graceful fallback on error, 400 on missing title, 401 on missing token, and 429 on rate limit duplicate request.

## 2. Key Questions (Assignment & PDF Requirements)

### Q1: Why must AI APIs always be called from the backend rather than directly from the frontend?
1. **Credential Protection:** Any API key included in client JavaScript, environment variables prefixed with `VITE_`, or browser network requests is completely public and can be extracted, stolen, and abused in seconds.
2. **Abuse Prevention & Rate Limiting:** The backend acts as a gatekeeper to enforce per-user rate limiting (e.g., 1 request per title per minute) and input validation, preventing rogue users from exhausting monthly AI quota.
3. **Data Scrubbing & Isolation:** The backend can sanitize inputs and prevent accidental leakage of sensitive session tokens or internal identifiers to external AI providers.

### Q2: What is "Graceful Degradation" and why is it essential for AI features in a CRUD app?
- **Definition:** An architectural pattern where the failure of a secondary, non-critical enhancement (AI description generation) does **not** degrade, crash, or block the core functionality of the application (creating, editing, and checking off tasks).
- **Implementation:** When Groq times out or returns an error, the backend catches the exception, logs it server-side, and returns HTTP 200 with `fallback: true`. The frontend displays a friendly inline notification reminding the user they can enter the description manually. The task creation button remains fully operational.

### Q3: What privacy and data governance concerns arise when integrating third-party AI APIs?
1. **Data Sovereignty & Third-Party Sharing:** Every prompt sent to an external LLM leaves your controlled infrastructure. Any user information in the payload is transmitted to the third-party provider's servers.
2. **Data Minimization Principle:** Never transmit passwords, emails, auth tokens, database IDs, or confidential user metadata. In our implementation, **only the task title** is transmitted to Groq.
3. **Human-in-the-Loop Transparency:** Users must always be informed that text was generated by AI and must be given full control to inspect, edit, or delete the suggestion prior to saving.

## 4. 5 Likely Viva Questions & Concise Answers

### 1. What model and temperature were configured for the Groq integration?
We used the `llama-3.1-8b-instant` model with a temperature of `0.5` and `max_tokens` of `120`. A lower temperature (0.5) reduces hallucination and ensures focused, concise, and predictable task descriptions.

### 2. How does `AbortController` work in Node.js fetch requests?
`AbortController` allows aborting in-flight HTTP requests. We initialize `const controller = new AbortController()` and pass `controller.signal` to `fetch()`. A timer triggers `controller.abort()` after `AI_TIMEOUT_MS` (8000 ms), canceling the socket connection if Groq takes too long to respond.

### 3. What HTTP status code is returned when a user requests multiple AI generations too quickly?
HTTP **429 Too Many Requests**, accompanied by a JSON envelope: `{ error: "Please wait before requesting another suggestion", retryAfterSeconds }`.

### 4. Why is the AI suggestion editable by the user rather than auto-saved directly to the database?
To enforce **Human-in-the-Loop** verification. LLM completions can contain hallucinations or inaccurate assumptions. By populating the suggestion into an editable textarea with a disclaimer, the user retains full agency to accept, edit, or reject the text before committing it to MongoDB.

### 5. What is the difference between passing `fallback: true` with HTTP 200 versus returning HTTP 500 on AI errors?
Returning HTTP 500 signals an unhandled application server error and can trigger global frontend error boundaries or toast error alerts that alarm the user. Returning HTTP 200 with `{ fallback: true }` indicates that the request was processed gracefully and allows the UI to handle the lack of an AI suggestion quietly as an expected alternative state.
